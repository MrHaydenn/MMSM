# Publishing MMSM updates

The client is ready for an owner-selected public HTTPS feed. No host, account or public release has been created by this package. Releases delivered in this conversation are not automatically published.

## Release workflow

1. Finish and test the desired version. Set the stable `major.minor.patch` version in `mmsm/__init__.py`, the frontend footer/asset cache keys and provider user agent. Increase it for each release.
2. Choose the final public HTTPS URL for the update ZIP, then run from the project directory:

   ```sh
   python tools/build_release.py --url https://YOUR-HOST/releases/MMSM-0.6.0-update.zip
   ```

3. Upload the generated `release/MMSM-0.6.0-update.zip` first. Upload `release/latest.json` last at a stable public HTTPS URL. The JSON contains version, ZIP URL and SHA-256. The builder creates files locally; it does not publish or use account credentials. Use the actual version/URL for subsequent releases.
4. In MMSM Settings, set Release feed URL to that stable `latest.json` address and save. Click Check for updates. Later versions appear automatically during six-hour checks and as a notification. The current or an older release is never offered as an upgrade.
5. Stop Minecraft servers and wait for downloads/backups/other operations to finish, then click Update MMSM. It verifies and stages the release, restarts the manager and reconnects the page. Only servers with AutoStart enabled launch afterward.

The update ZIP is different from the full source/distribution ZIP delivered here: it contains only program paths relative to the project root, with no enclosing distribution folder. Always use the builder for the feed artifact. Preserve the full source ZIP separately for a manual install/recovery.

## Trust and limits

Only an unrestricted administrator can configure/check/install manager updates. Choose a release host you control and trust: the feed author supplies executable program code. HTTPS and SHA-256 check transport/package integrity; this is not an independently signed release system. HTTP, local/private addresses, credentials in URLs, unsafe redirects, ZIP path escapes, symlinks, duplicate paths and data-folder entries are rejected. ZIP downloads are limited to 32 MiB, expansion to 128 MiB and entries to 2,000.

The feed format is:

```json
{"version":"0.6.0","url":"https://YOUR-HOST/releases/MMSM-0.6.0-update.zip","sha256":"64 lowercase hexadecimal characters generated by the builder"}
```

Supported flow: normal Python MMSM launch, writable program directory, same Python version and arguments retained. Windows execution remains a host acceptance check. Immutable/container-image deployments should update their deployed image instead; in-container file changes may disappear when recreated. The updater does not install a new Python interpreter or migrate arbitrary future database formats.

## Recovery

Replacement errors restore original program files and remove newly added files, then restart the old version. Interrupted replacement leaves a journal that MMSM attempts to roll back at its next startup. Keep a normal full backup before adopting a release. If an interruption or a defective release prevents the Python entry point from loading, restore the previous program files manually from `data/updates/rollback` or your previous full distribution, keeping `data`, `Servers`, `Backups` and `dependencies`. A successful replacement is not a promise that every behavior in a future release is bug-free. Review the terminal if restart does not complete.
